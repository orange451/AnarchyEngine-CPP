# Anarchy Engine

Anarchy Engine is a game engine and studio for building a place and playing it. The place is a tree of instances. Gameplay is Luau that reads and changes that tree. Test runs the simulation. Stop puts the place back to what you authored.

You use it to make a small game in one window: arrange instances, write the scripts that move them, run the place, and edit again from the restored world. The desktop studio is the way in. The engine underneath is what keeps the live place, the scripts, and the picture on screen in step with each other.

## The place

Every object in the world is an instance. It has a name, a parent, and children, and siblings may share a name. The root of that tree is the place a script sees as `game`.

Everything in the tree is a `DataModel`: it has `Name`, `Parent`, `FindFirstChild`, and the rest. What `Instance.new` makes is an `Instance`. `game` is a `Game`, a `DataModel` that is not an `Instance`, since a script cannot make one; `GetService` is on `game` alone. A `Parent` is any `DataModel`.

`game` holds five scene services and nothing else, in this order:

- `Workspace` is what the place shows. Anything may go in it; what can render, renders.
- `Lighting` is how the scene is lit, through its properties: `Ambient`, `Brightness`, `FogColor`, `FogStart`, `FogEnd`, `Exposure`, `Saturation`, and `Gamma`. The Scene View reads `Ambient`, `Exposure`, `Saturation`, and `Gamma`; the others are not drawn yet. Lights in it shine as they do in `Workspace`, and a `Skybox` in it is the sky.
- `Storage` keeps assets a place uses at runtime. Nothing in it renders or runs.
- `Scripts` holds scripts that run at runtime.
- `Gui` holds the screen GUIs: every `ScreenGui` in it is drawn over the Scene View, in edit mode and in play. Scripts in it run, as they do in `Workspace`.

Lights cast shadows in the Scene View. A `PointLight` or `SpotLight` casts them when its `Shadows` is true (false by default); a `DirectionalLight` casts them by default, out to `ShadowDistance` studs from the camera (100). PointLights and SpotLights share one shadow atlas: each light's map gets a tile sized by how big the light looks, judged by its `Radius` against its distance rather than any fixed number of studs, so a place built at any scale behaves the same; a light that looks tiny casts none. A map is drawn again only when the light, or something within its `Radius`, changes, and only so much is redrawn each frame, so many shadowed lights stay cheap. A light that moves may trail its shadow by a frame or two. A DirectionalLight's shadows come in four cascades fitted so their edges hold still as the camera moves and turns; only the first shadowed DirectionalLight casts them. A light's own Prefab never shadows it, and see-through objects cast no shadow.

A scene service is a `SceneService`, a `DataModel` that is not an `Instance`, like `Game`. Every place has each of them, always: none can be moved, renamed, destroyed, or made with `Instance.new`, and anything else put directly under `game` is refused with a message that says to put it in `Workspace`. Scripts reach them as `game.Workspace` or `game:GetService("Workspace")`, and `workspace` is `game.Workspace`. `getmetatable` on any instance gives `"The metatable is locked"`.

`game` also holds `Assets`, a hidden `GameService`. The Game Explorer does not show it or anything under it, though scripts, Properties, and MCP see it like any instance. Assets holds five categories, always in this order: `Materials`, `Prefabs`, `Meshes`, `Textures`, and `Audio`. Each holds only its own asset class and Folders, at any depth; a Prefab holds only Models, and every other asset holds nothing. No one can move, rename, or destroy Assets or a category, the way no one can a scene service. Scripts reach them as `game.Assets.Textures` or `game:GetService("Assets")`.

The six asset classes: `Texture`, `Mesh`, and `Sound` each have a `Path`, a string relative to the project's resources folder, such as `textures/brick.png`, with `/` separators; an absolute path, a drive letter, a backslash, or a `..` segment is refused. A `Sound` also has `TimeLength`, read-only: how long its file plays, in seconds, or 0 when there is no file that plays. `Material` has four `Texture?` references: `DiffuseTexture`, `NormalTexture`, `RoughnessTexture`, and `MetalnessTexture`. `Prefab` holds `Model`s as its only children. `Model` has a `Mesh?` and a `Material?` reference. A reference property is the class name with `?`, such as `Texture?`; it is held by the target's GUID and reads `nil` when the target is gone, as after a destroy or in a file that names a GUID nothing holds.

`GameObject` is the instance that occupies space. It carries a transform, a velocity, and a `Prefab?` reference. Scripts move a GameObject through `Transform`, a `Matrix4`: `Transform.Position` is where it is, and adding a `Vector3` to the `Transform` moves it and keeps its rotation. Right-clicking a Prefab in the Assets pane and choosing Add as GameObject, or dragging it onto a Scene View, puts a GameObject named after it in `Workspace`, with `Prefab` set to it; nothing is copied. The Scene View draws each Model of that Prefab at the GameObject's transform: the Model's Mesh, whose `Path` names an AMESH file under the project's resources folder. A GameObject with no Prefab draws nothing. A Mesh can build its own geometry from shapes: `AddBox(size, position?)`, `AddSphere(radius, segments?, position?)`, `AddCylinder(radius, height, segments?, capped?, position?)`, `AddCone(radius, height, segments?, capped?, position?)`, `AddPlane(width, depth, position?)`, and `AddTeapot(size, position?)` each add to the Mesh's AMESH file, and `Clear()` empties it. Shapes are centered on `position`, the origin by default, except the teapot, which stands on it. A Mesh with no `Path` gets `meshes/<Name>.<guid>.amesh` first. While the place is stopped they write to the project's resources folder, or an untitled place's scratch folder, and never write over a file that is not AMESH; undo puts back a `Path` they set, but not the file. During play, from a script or the command line, they leave the file alone and change a copy for the session instead, starting from the file the first time: the Scene View draws the copy on the next frame, and Stop drops it, so the Mesh draws its file again. Each change copies the whole mesh and uploads it again, which suits shapes built now and then more than a mesh rebuilt every frame. `Script` and `ModuleScript` hold Luau source; both are a `LuaSource`, which has `Source`. Only a `Script` has `Enabled`, since a `ModuleScript` runs only through `require`. Any other instance is a node in the tree, with a name, a parent, and signals.

Creating an instance, parenting it, or writing a property is how the place grows. Those writes are what explorers, scripts, and the play session all share.

`Skybox` is the sky around the place, and lives only under `Lighting` (through Folders too); put anywhere else, it is refused with "A Skybox must be in Lighting". Its `Image`, a `Texture?`, is an equirectangular panorama, such as an HDRI from [Poly Haven](https://polyhaven.com/hdris): the Scene View draws it behind everything and lights every surface with it, through image-based lighting, so a rough surface takes its soft light and a smooth metal mirrors it. A Radiance `.hdr` keeps light brighter than white; a PNG, JPEG, or any other image is taken as sRGB. OpenEXR is not read, and says so in the console; pick `.hdr` when downloading. `Exposure` (0 to 10, 1 by default) scales the sky and its light, `LightScale` (0 to 10, 1 by default) scales only the light the sky gives surfaces, leaving the sky behind them as it looks (lower it when a bright sky washes out shadows), `Rotation` turns it about Y in degrees, wrapping into 0 to 360, and `Tint`, a `Color3`, multiplies it. With no Skybox, or no `Image`, surfaces get the flat stand-in sky light they always had. When `Lighting` holds two, the first in the tree is the sky. The sky's lighting is filtered on the GPU when the image changes, not when the other properties do; an image wider than 4096 pixels is halved first.

`PhysicsObject` is a rigid body, simulated by [Box3D](https://github.com/erincatto/box3d) while the place plays and it is anywhere in `Workspace`; anywhere else it is only data. Its `GameObject` property names the GameObject it moves: the body starts at that GameObject's Transform and writes it back as it falls, tumbles, and collides, keeping the GameObject's scale. With `GameObject` nil, a PhysicsObject whose parent is a GameObject moves that parent instead; the link is only where it sits, so moved anywhere else it stops moving it, and `GameObject` still reads nil. With neither it is an invisible collider placed by its own `Transform`. `Shape` is an `Enum.PhysicsShape`: `Box`, `Sphere`, `Capsule`, `Hull`, or `Custom`. `Size` sizes it: a Box's extents, a Sphere's diameter in X, a Capsule's diameter in X and height in Y, and the box a Hull's or Custom's mesh is fitted to. A Hull is the convex hull of the vertices of its `Mesh`; a Custom is that whole Mesh, every triangle, so it has the Mesh's hollows and steps. Box3D lets a whole mesh collide only on a static body, so a Custom is its whole Mesh while `Anchored`, and a Hull of it, with a warning, while not. Properties shows `Mesh` only for a Hull or a Custom; with no Mesh, or none it can build, either is a Box and says so once. `Anchored` makes it static. `Mass`, `Friction`, `Bounciness`, `LinearDamping`, and `AngularDamping` are what they say, and `Velocity` and `AngularVelocity` are world space, in units and radians per second. Writing `Transform` or a velocity during play moves the body, and so does writing its GameObject's Transform; what physics itself writes fires no `Changed`. When two PhysicsObjects name one GameObject, the first in the tree moves it and the other has no body. Gravity is 9.81 down.

Every class with a `Transform` is a `PVInstance`: `GameObject`, its subclasses `Camera`, `PointLight`, and `SpotLight`, and `PhysicsObject`. `PVInstance` adds no members and cannot be made itself, but `IsA("PVInstance")` is true of each, and code that only needs a position reads it through that class.

`SoundEmitter` plays a `Sound`, through [miniaudio](https://github.com/mackron/miniaudio), while the place plays and it is anywhere under `game`. `Play()` starts its `Sound` from `TimePosition`, or from the start when it is already playing, and `Stop()` stops it and puts `TimePosition` back to 0. When its parent is a PVInstance it is heard from that PVInstance's position, read every frame, so it moves with it; anywhere else it is 2D, the same in both ears at any distance. Destroying the SoundEmitter, its PVInstance, or its Sound stops it in the same frame. `Volume` (0 to 5, 0.5 by default) and `Pitch` (0 to 5, the playback speed) are clamped to their range. `RollOffMode` is an `Enum.RollOffMode`, miniaudio's attenuation models: `Inverse`, `Linear`, `Exponential`, or `None`, which neither fades nor pans. Within `RollOffMinDistance` it is at full volume, and past `RollOffMaxDistance` it gets no quieter, both from 0 to 512. `Looped` plays it again from the start each time it ends; one that does not loop stops at its end. `TimePosition` follows the sound as it plays, and writing it seeks. `IsPlaying` is read-only. The listener is `Workspace.CurrentCamera`, looking down its -Z. Pause holds every sound where it is, and Stop silences them all. A Sound's file is WAV, MP3, FLAC, or Ogg Vorbis; one that cannot be played says so once in the console.

## Screen GUIs

GUIs are instances too, as they were in the legacy engine, laid out the way [JadeFX](https://github.com/orange451/JadeFX_CPP) lays out its nodes and styled with CSS. A `ScreenGui` under `game.Gui`, directly or through Folders, fills the Scene View; what is inside it, through a chain of GUI instances, is drawn on top of the scene. A GUI anywhere else is only data.

Every GUI class is a `GuiBase`: `ClassList` (CSS classes, separated by spaces), `Style` (inline CSS), `Size` (a `Vector2`, the preferred size in points; 0 on an axis leaves it to the content and CSS), `Alignment` (an `Enum.GuiAlignment`, where its children sit), `Visible`, and `MouseTransparent`. `Pane`, `HBox`, and `VBox` are a `GuiBasePane`, with `BackgroundColor` and `BackgroundTransparency`: a Pane stacks its children by Alignment and starts 100 by 100, and an HBox and a VBox put them in a row or a column, `Spacing` apart. A `Label` has `Text`, `TextColor`, and `FontSize`; a `Button` has `Text`; a `TextField` has `Text`, which typing changes, and `Prompt`.

Every GuiBase fires `MouseClicked`, `MousePressed`, `MouseReleased`, `MouseEntered`, and `MouseExited`, and a Button and a TextField fire `Action`, on a click or Enter. None passes arguments. A press or click on a GUI is heard by everything it is inside, as in a web page, and reaches `UserInputService` with `gameProcessedEvent` true; a press on a ScreenGui's own empty area goes to the scene as if no GUI were there.

A `CSS` instance styles its parent GUI and everything in it. Type selectors are the class names in lowercase (`screengui`, `pane`, `hbox`, `vbox`, `label`, `button`, `textfield`), `#Name` matches an instance's Name, `.class` its ClassList, and JadeFX's pseudo-classes such as `:hover` and `:active` work. What CSS sets wins over the properties: `background-color` over BackgroundColor, `color` over TextColor, `width` over Size. Double-click a CSS in the Game Explorer to edit it.

```lua
local hud = Instance.new("ScreenGui", game.Gui)
hud.Alignment = "BottomCenter"
local bar = Instance.new("HBox", hud)
bar.ClassList = "toolbar"
local play = Instance.new("Button", bar)
play.Text = "Play"
play.Action:Connect(function() print("play") end)
local sheet = Instance.new("CSS", hud)
sheet.Source = ".toolbar { padding: 10px; spacing: 8px; border-radius: 8px; }"
```

## Scripts

A script runs against the live place. It gets `game` for the root, `workspace` for `game.Workspace`, and `script` for itself. From there it creates instances with `Instance.new`, finds children, reads and writes properties, and connects to signals such as `Changed`. `task.wait`, `task.spawn`, `task.defer`, and `task.delay` schedule work on the simulation clock. A `ModuleScript` runs when another script calls `require`.

```lua
local camera = workspace:FindFirstChild("Camera")
assert(camera)
local home = camera.Transform

while true do
    task.wait(0.5)
    camera.Transform = home + Vector3.new(0.45, 0, 0)
end
```

A script runs only under `Workspace`, `Scripts`, or `Gui`, at any depth. It starts when it is there, enabled, and the place is playing. Moved out, into `Storage` or out of the tree, it stops; moved back, it starts again from the top. A move among `Workspace`, `Scripts`, and `Gui` does not restart it. A `ModuleScript` can be required from anywhere. It runs on the simulation, on the same clock as Heartbeat. The code is sandboxed to the libraries the engine opens: the Luau base libraries, `task`, and the instance API.

`game:GetService("UserInputService")` is the keyboard and mouse, the way Roblox's `UserInputService` has them. Click the scene view during a test to give it the keyboard. `InputBegan`, `InputChanged`, and `InputEnded` fire with an `InputObject`, whose `KeyCode`, `UserInputType`, `UserInputState`, `Position`, and `Delta` say what happened, and `gameProcessedEvent`. `IsKeyDown`, `IsMouseButtonPressed`, `GetKeysPressed`, `GetMouseButtonsPressed`, and `GetMouseLocation` ask what is held now. Positions are points from the scene view's top-left corner. As in Roblox, `GetMouseLocation` returns a `Vector2`, and an `InputObject`'s `Position` and `Delta` are `Vector3`s whose z is 0, except that a `MouseWheel` input's `Position.Z` is how far the wheel turned. A key still held when the view loses focus gets its `InputEnded` then, and Stop forgets whatever was held. Setting `MouseBehavior` to a lock locks the pointer only in the scene view that has focus, the one last clicked. Shift+Esc takes the focus from that view and frees the pointer until you click the view again, which locks it again; `MouseBehavior` keeps what the script set.

```lua
local UserInputService = game:GetService("UserInputService")

UserInputService.InputBegan:Connect(function(input, gameProcessedEvent)
    if input.KeyCode == Enum.KeyCode.Space then
        print("jump")
    end
end)

game:GetService("RunService").Heartbeat:Connect(function(dt)
    if UserInputService:IsKeyDown(Enum.KeyCode.W) then
        print("forward", dt)
    end
end)
```

## Play

The simulation starts paused, so the place holds still while you edit. Test captures that place, starts every eligible script, and steps the world at 60 Hz. A frame can take several physics steps, then Heartbeat, which wakes `task.wait` and steps the instances in the tree.

Stop ends the session. Scripts are aborted, instances created during play are gone, and property changes revert to the captured place. Text you still have open in a script editor is written back onto those restored scripts, so the edit survives the stop.

## Projects

A project is a directory, and it is meant to live in git. `project.json` names it. `src/` holds the authored tree, one file per instance, and `resources/` is where textures, meshes, and audio will go. The live place is a working copy: loading reads `src/`, and saving writes back only the files whose bytes changed.

Every instance has a GUID that never changes, and every file is named `<Name>.<guid>`. Two siblings may both be called `Part`; they are two files. Adding a third `Part` adds one file, and renaming one moves only that file. An instance with children becomes a folder holding its own `init.json`. A script is a `.luau` file with a `.meta.json` beside it, so its source never lands inside JSON. Keys the engine does not know are kept as they are.

Each scene service is a file or folder under `src/` like any instance, with a fixed GUID, its class name in lowercase: `src/Workspace.workspace/` holds what is in `Workspace`. Any other instance directly under `game` is an error. A service whose file is missing is made at its defaults and written at the next Save. `Assets` and its five categories follow the same rule: `src/Assets.assets/` holds `Textures.textures/`, and so on. A project saved before Assets existed loads with an empty Assets tree, and the next Save writes it.

File > New starts an empty, untitled place. File > Open picks a project folder, File > Save writes to it, and File > Save As names a new folder and writes the whole project there. A place that has never been saved asks for a folder on its first Save. Until then, what it adds to resources, such as imported files and a Mesh's shapes, goes in a scratch folder of its own, `AnarchyEngine/untitled-<id>/resources` under the system's temporary folder; its first Save moves those files into the project's `resources/`, where their Paths name them as before. New, Open, and closing the studio delete that folder, and the system clears its temporary folder of any a crash left behind. A toast at the bottom right of the window says what each one did, such as `Saved MyPlace (2 files changed)`. The project on disk can change while it is open, as by git, another editor, or Claude. The studio compares the disk with the place when its window comes back to the front, before each Save, when a test stops, and from File > Reload from Disk; it waits while a rename or a Properties field is being typed in, and during a test it only says that changes wait for Stop. It compares each instance's file property by property against what was last opened or saved. What only the disk changed loads into the place as one undo step, with a toast such as `Loaded 3 changes from disk: Part, Door, and 1 more`, and a file only formatted differently is no change. What both sides changed differently is a conflict: a warning count at the right end of the ribbon shows how many, and clicking it opens the Conflicts window beside the left explorer. There each instance is a row with its conflicting properties under it, the studio's value and the disk's side by side. Each row picks IDE or Disk, an instance's row picks for all of its properties, and All IDE and All Disk pick for everything; Apply applies the picks as one undo step, and a row with no pick stays. A row can also be a whole instance, deleted on one side and changed on the other. Clicking a row selects its instance in the explorers, and Refresh checks again. Save with conflicts left lists them, says to check the Conflicts window, and offers Show Conflicts, Overwrite All, which keeps the studio's side of each and saves, and Cancel. When `src/` does not read as a project, as mid-checkout, nothing loads and the Conflicts window says which file; Save then still never writes over a file that changed on disk since it was opened or saved. The title shows `*` while the place differs from what is on disk; New, Open, and closing the window offer to save it first. An edit undone back to the saved state does not count, and neither does anything a test does. The dialogs are the system's own: Cocoa on macOS, the Windows file dialog, and zenity or kdialog on Linux. `AnarchyEngine-CPP <folder>` opens a project at launch.

Saving during play writes the place as it was when Test started, never what the session created. Undo history, caches, and editor layout stay out of the tree; `.studio/` is ignored for them.

## The studio

The window is the studio. Explorers on either side list the place by instance name, with `Workspace` open to start. The studio starts on a new place, as File > New makes one: empty but for a `Camera` in `Workspace`. The scene view draws each GameObject in `Workspace` that has a Prefab, seen from a Camera chosen in the list at its top right, and it keeps painting while the simulation is paused. A mesh file that is missing or not AMESH draws nothing, and the console says why; a mesh file that changes is read again within a second. The script editor opens a script from its row, highlights Luau, with datatypes such as `Vector3`, `Instance`, and `Enum` in their own color, and completes names and members as you type. A `.` at the start of a line, outside every function and block, lists the ModuleScripts in the place and the services whose names start with what you type after the dot; choosing one writes the line that gets it, so `.Conf` becomes `local Config = require(game.Workspace.Folder.Config)` and `.UserIn` becomes `local UserInputService = game:GetService("UserInputService")`. The console shows `print` output and script errors. A printed table shows as `{...}`, or `{}` when it is empty. Clicking `{...}` opens it one level at a time, written the way Luau writes a table, as it was when printed; clicking its `{` closes it. A table with a `__tostring` prints what that returns and does not open. Clear Output, from a right-click on the log or Cmd+K (Ctrl+K elsewhere), empties it. Its command line runs Luau against the same place while play is stopped.

Cmd+F (Ctrl+F elsewhere) in a script opens the find bar at the editor's top right, as in VS Code. It starts from the selection, or from the name under the caret, and highlights every match, the current one more strongly, with a count such as `2 of 6`. Each match is also a band down the left half of the editor's scroll bar, and each error, warning, and note the script's analysis finds is one down the right half, so the whole script shows at a glance; clicking a band scrolls to it. Aa matches case, ab matches whole words, and .* reads the text as a regular expression; Cmd+Alt+C, W, and R (Alt elsewhere) flip them. Enter and Shift+Enter, the up and down buttons, F3, or Cmd+G step through the matches. The replace field starts hidden. The chevron shows it, and Cmd+Alt+F (Ctrl+H) opens the bar with it: Enter or its first button replaces the current match and moves on, and Cmd+Enter or the second replaces every match as one undo step. A regular expression's replacement can use `$1` and `$&`. Escape closes the bar.

Edit > Find in Scripts, Cmd+Shift+F (Ctrl+Shift+F), docks a Search pane beside the Game Explorer that does the same across every Script and ModuleScript in the place. Each script with a match is listed with its path and how many matches it has, with its matching lines under it; clicking a line opens the script there with the match selected. Its replace field starts hidden too; Replace in Scripts, Cmd+Shift+H, shows it. Replace All asks first, then writes through open editors, where their own undo takes it back, and into every other script as one undo step in the place. While replace is shown, the button on the row under the pointer replaces just that line, or that whole script. The results keep up with edits, including text an editor has not written to its script yet.

Window > Assets docks the Assets pane in with the console, by default. It shows the tree under `Assets`: a sidebar of the five categories, back and forward buttons, and a path bar with a clickable crumb per level. A Search field with × replaces the view with a flat list of every match under the current folder, ignoring case, each with its path. A toolbar toggle switches between three views, Icons, List, and Columns, remembered in `preferences.json` as `assetsView`: `"icons"`, `"list"`, or `"columns"`. Icons is a wrapping grid of tiles, one per child; List is a tree table of Name, Kind, and Path, sortable by column; Columns is one column per level, ending in a preview of a selected asset's icon, name, class, and Path or references. A click selects, Ctrl (Cmd) and Shift extend the selection as in the explorers, and the pane shares that selection with them and with Properties. Double-click opens a Folder, and edits a Prefab. A Prefab is one item: it does not open, and its Models are not shown or found by Search. Clicking a selected item again after a pause renames it; Delete deletes the selection; Cut and Paste move items; dragging moves the selection onto a folder, a sidebar category, or a crumb, dragging an asset onto a reference row in Properties sets it, and dragging Prefabs onto a Scene View adds each as a GameObject, as Add as GameObject does; over the view, the pointer shows a plus. A right-click on an item offers Rename, Cut, Paste, and Delete, and a Prefab's also offers Edit and Add as GameObject; a right-click on empty space offers New *kind*, New Folder, and Paste, and first, in Textures, Audio, and Prefabs, or a Folder under one, Import Texture…, Import Sound…, or Import Model…, which picks files and imports them into that folder without asking, as a drop would. A refused move is a toast, and each action is one undo step.

Dropping image, sound, or model files anywhere on the studio a pane does not take them asks first, then imports them into the place as one undo step, and selects what it made. An image (PNG, JPEG, TGA, and the other formats a Texture reads) is copied into `resources/textures/` and becomes a Texture in `Assets.Textures` named after the file. A sound (WAV, MP3, FLAC, or OGG) is copied into `resources/sounds/` and becomes a Sound in `Assets.Audio`. A model (OBJ, FBX, glTF or GLB, DAE, 3DS, PLY, or STL), read with [Assimp](https://github.com/assimp/assimp), becomes a Prefab in `Assets.Prefabs` named after the file, with one Model for each material it draws with. Each node's transform is baked into the vertices, and everything one material draws is one Mesh, an AMESH file in `resources/meshes/<model>/`. The Meshes, Materials, and Textures go in a Folder named after the model in each category. A Material takes the file's color, emissive, metalness, roughness, and opacity, and its diffuse, normal, roughness, and metalness maps; a glTF metallic-roughness map is split into a roughness map and a metalness map, since a Material reads each from its red channel. A texture is looked for where the file says, then by name, ignoring case, beside the model and in the folders under it and beside it; one embedded in the file is written out. The textures are copied into `resources/textures/<model>/`, unless they are already under `resources/`. Importing the same model again gives it a second folder, `<model>-2`. Skinned meshes come in static, in their bind pose; bones and animations are not imported yet. What a model had that was left out, such as a texture not found, is printed to the console. The file is read before the studio moves on, so a large model holds the window while it reads. An LLM client imports the same way through the MCP tool `import_assets`, which takes absolute paths, reads the files without holding the window, and returns what each file made or why it failed. Importing needs a stopped test. A place that has never been saved imports into its scratch folder, described under Projects, and its first Save brings the files into the project.

Window > New Terminal docks a new terminal in with the console each time it is picked, running your shell in the project's folder: PowerShell on Windows (PowerShell 7 when it is installed), and your login shell on macOS and Linux. It is a real terminal on a pseudo-terminal (ConPTY on Windows, forkpty elsewhere), so full-screen and interactive programs such as `vim`, `git log`, and `claude` work in it, in color. Its basic colors follow the theme, darker on a light one, and text too faint against its background is darkened or lightened until it reads, as VS Code's terminal does, so programs made for a dark terminal stay readable on a light theme. Block elements and box-drawing lines, such as Claude Code's mascot and the borders programs draw, are drawn as shapes that fill their cells on whole pixels rather than from the font, so they join without gaps. While it has focus, keys go to the program, Ctrl+C, Ctrl+S, Tab, and Escape included; Cmd shortcuts on macOS and Ctrl+Shift ones elsewhere still reach the studio. Paste is Cmd+V on macOS, Ctrl+V on Windows, and Ctrl+Shift+V on Linux. The wheel scrolls back through what went off the top, and typing comes back to the bottom. The tab shows the title the program sets. The shell keeps running while its tab is hidden behind another, and closing the tab ends it. Terminals are not kept in the layout, so a new studio starts with none. When the shell exits, Enter starts another.

A click on a row selects that instance. Ctrl (Cmd on macOS) and a click adds or removes a row, and Shift and a click selects every row from the last one clicked. Both explorers show the same selection, and so do scripts: `game:GetService("Selection")` has `Get`, which returns the selected instances, and `Set`, which replaces them and shows in the explorers on the next frame. Delete removes every selected instance as one undo step, and Cut takes them all out of the place; a selected child goes with its selected parent. Paste puts everything cut under the row, in the order it was shown, and selects it. Dragging a row moves it, and the rest of the selection with it when it is selected: dropped on the middle of a row, it goes inside that instance; dropped on a row's top or bottom edge, it goes beside it. While you drag, a box around the row or a line between rows shows where it will land, and under the last row of a branch the pointer's distance from the left picks how deep the line goes. A move is one undo step, a row never goes inside itself, and Escape cancels. Cut, paste, and rename work on any instance but a scene service, which only takes a paste; something inserted or pasted at the top of the tree goes into `Workspace`. Rename edits the name in place on its row: Enter keeps it, and Escape or a click elsewhere drops it. Clicking a row again after a pause also renames it. Double-click a script to edit it. Double-click a `CSS` to edit its stylesheet in a CSS editor, highlighted as CSS and saved to its `Source` as you type. Double-click a Prefab, or pick Edit on it, and a Prefab editor docks beside the scene view, its tab named after the Prefab. Each Prefab has one editor at most, so editing one again brings its tab forward, and Prefab editors, like script editors, are not kept in the layout. The editor shows the Prefab's Models as cards, each with its name, whether it is ready to draw, and a slot for its Mesh and one for its Material. Clicking a slot opens a picker of every Mesh or Material in Assets, with its folder: typing filters it, Up and Down move, Enter picks, Escape closes, and None or the slot's × clears it. Add Model, or the New Model tile, adds a Model and opens its Mesh picker, and picking a Mesh opens its Material picker, so two picks make a whole Model. A Model still called Model, or named after its Mesh, takes the name of a new Mesh. Dragging assets from the Assets pane onto a slot fills it, onto a card fills the slot that fits, and onto empty space adds a Model holding them. A click on a card selects its Model for Properties, Delete deletes the selected ones, and F2, Enter, or a double-click on the name renames one. Each change is one undo step. Properties lists what every selected instance has in common: Name, Parent, and ClassName first, then the rest by name. A value the selection does not agree on is blank. Typing a value and pressing Enter, or leaving the field, writes it to every selected instance as one undo step; a blank field that was never typed in writes nothing, and Escape drops what was typed. A Vector3 axis writes only that axis. Clicking into a field, or tabbing to it, selects its value, so typing replaces it; a click that drags selects what it drags over instead. Tab and Shift+Tab move through the fields that can be typed in, a Vector3's X, Y, and Z in turn, and write the one they leave. A Transform shows as its name with an arrow, then a Position line and an Orientation line, each an X, Y, and Z tinted red, green, and blue. Orientation is in degrees, turned about Y, then X, then Z; typing one axis changes only that axis of the Transform. Clicking the arrow or the name folds the row. Parent shows the instance's name, with its path on hover: clicking the name takes the next instance clicked in an explorer, clicking it again cancels, x clears it, and a Parent that would put an instance inside itself is refused. Undo in a Properties field first undoes the typing in that field, then the place. The ribbon under the menu bar runs the play session: Test starts it, Pause and Resume hold and continue it, and Stop puts the place back. F5 is Test, or Resume when paused, and Shift+F5 is Stop. Scene View: right-drag to look around, W/A/S/D to fly, E/Q to rise and sink. The Filter field at the top of each explorer hides rows whose name does not contain what you type, keeping the branches that lead to a match; its × empties it, and Escape leaves the field. Escape leaves every text field that way, keeping its text, such as the console's command line, the Search pane's fields, and those in Preferences. A field with its own use for Escape keeps it: a rename or a Properties value drops what was typed as it leaves, and the find bar closes. Escape in the tree clears the selection, and F opens the branches above the selected instances and scrolls to them. The widgets and the window come from [JadeFX](https://github.com/orange451/JadeFX_CPP).

### Themes and preferences

File > Preferences, Cmd+, (Ctrl+, elsewhere), opens the Preferences window. Its Appearance tab picks the theme the studio draws with: Light, Dark, Dracula, Nord, One Dark, Monokai, Solarized Dark, Solarized Light, Classic Studio (the colors of Roblox Studio's classic dark theme), or one of your own. The choice is kept in `preferences.json` in the studio's config folder, `~/Library/Application Support/AnarchyEngine` on macOS, `%APPDATA%\AnarchyEngine` on Windows, and `$XDG_CONFIG_HOME/anarchy-engine` (else `~/.config/anarchy-engine`) on Linux, and the studio starts in it.

A theme is a CSS file of custom properties on `:root`. `--theme-name` names it, and `--theme-base`, `light` or `dark`, picks the JadeFX look under it. The `--ide-*` variables are the studio's colors, such as `--ide-syntax-keyword-color`; JadeFX's own, such as `--accent-color`, can be set too, and a value may use `var()`. A theme sets only what it changes. The rest comes from the shipped theme it names in `--theme-extends`, such as `nord`, or else the shipped theme of its base. The shipped themes are the files in `resources/themes`; each but Light and Dark starts with its published palette, and every color after it names one of those. Nothing but variables is read.

```css
:root {
    --theme-name: "Solarized Dark";
    --theme-base: dark;
    --ide-editor-color: #002b36;
    --ide-syntax-keyword-color: #859900;
}
```

The Appearance tab lists every color with its variable's name, in groups such as Studio, Script Editor, and Console, each closed until its heading is clicked. Another click closes it again, and a filter narrows the list, opening every group with a match. A changed color shows in the studio at once. Reset gives a color back what the theme under it has, Revert drops every change, and Save writes them. The shipped themes are built in, so changes to one are saved with Save As, as a new theme that extends it. A saved theme keeps only the colors that differ from the theme it extends. Import copies a theme file into the `themes` folder beside `preferences.json` and picks it, and so does dropping a `.css` file on the window. Open Themes Folder shows that folder; a file put there by hand is listed the next time Preferences opens. Delete removes one of your themes.

## Talking to an LLM (MCP)

The studio can run a [Model Context Protocol](https://modelcontextprotocol.io) server, so an LLM client can read and edit the place. It is off until you turn it on: File > Preferences, AI tab, check Let AI clients drive this studio. The choice is kept in `preferences.json` as `mcpEnabled`, and the server starts and stops at once. The first studio listens at `http://127.0.0.1:7777/mcp`; one opened while another has 7777 listens on any free port. A toast at the bottom right of the window says where, the AI tab shows it too, and if the server could not start, both the tab and the console say why.

The same tab connects Claude Code. Connect runs `claude mcp add` for you, registering the `anarchy-mcp` beside the studio for every folder you work in, and the tab shows whether Claude Code has this studio's bridge, another one (such as an older build's, which Connect replaces), or none. Disconnect takes it out, and Copy Command copies the command to run by hand. The tab looks for `claude` in `PATH`, then in `~/.local/bin`, and on Windows in npm's folder; when it is not found, Copy Command still works. Claude Code picks the server up when it next starts, or after `/mcp` in a running session.

Several studios can be open at once, so clients go through `anarchy-mcp`, a bridge the build puts beside the studio in `build/`. Other clients register it by hand, once, for every folder you work in. With Claude Code, that is what Connect runs:

```
claude mcp add anarchy --scope user -- /path/to/AnarchyEngine-CPP/build/anarchy-mcp
```

Each studio names its project and port in a `studios` folder beside `preferences.json`, and the bridge sends each tool call to one of them:

1. the studio `select_studio` picked, by project name, folder, or pid, until it closes;
2. else the one `--project <name|folder|pid>` names, when the bridge was registered with it;
3. else the only studio open;
4. else the studio whose project folder holds the folder the client was started in, so `cd MyGame && claude` talks to the studio that has MyGame open.

Otherwise a call fails and lists the open studios. Once the studio `select_studio` picked closes, calls fail until it picks another; `select_studio` with `""` goes back to the usual order. `list_studios` shows every open studio and which one calls go to, and `get_studio_info` asks a studio which project it has open. The entry of a studio that crashed is dropped the next time the bridge looks.

With only one studio open, a client that speaks MCP over HTTP can also connect to it directly, with the token described below: `claude mcp add --transport http anarchy http://127.0.0.1:7777/mcp --header "Authorization: Bearer <secret>"`.

The tools read the tree (`get_tree`, `find_instances`), read and set properties, create and delete instances, read and write scripts, get and set the explorers' selection, list classes and their Luau API, run Luau with `run_lua` and read what it printed, read the console with `get_output`, and start, pause, and stop a test with `playtest`. An instance is named by its id or by its path of names, such as `Folder.Part`. Edits go through undo like edits made by hand, and a chunk from `run_lua` shows in the console.

The server listens on the loopback address only, and refuses requests from a web page on another site. The environment decides over the AI tab's box, which then cannot be changed: `ANARCHY_MCP=0` turns the server off and any other value turns it on, and `ANARCHY_MCP_PORT` or `ANARCHY_MCP_TOKEN` turns it on too. `ANARCHY_MCP_PORT` pins the port, and the server does not start when that port is taken. Every request needs `Authorization: Bearer <token>`: each studio makes a random token when it starts and writes it in its registry entry, in a folder only you can read, and the bridge sends it from there. To connect a client directly, start the studio with `ANARCHY_MCP_TOKEN=<secret>`, which it uses instead, and give the client the same secret (with Claude Code, add `--header "Authorization: Bearer <secret>"`).
